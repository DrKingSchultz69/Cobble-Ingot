# Netheron problem research: how to do it

Goal: a **one-time snapshot** of the real, repeated problems people have had **up to now** with coding harnesses (Claude Code, Codex, Pi…), AI IDEs (Cursor, Zed…) and multi-model orchestrators. Then turn the biggest ones into Netheron features, with evidence behind every decision.

**This is a sprint with an end, not ongoing monitoring.** Evidence window: **2025-10-01 → 2026-10-08** (cutoff date). Anything posted after the cutoff is ignored. When the final report is written, the research is closed.

| [[synthesis]] | Problems grouped into themes and scored; role summaries | Day 5, once |

| [[report]] | **The final deliverable**: top problems, evidence, chosen solutions | Day 5, closes the research |

> [!tip] Reading this in Obsidian
> Open the **`docs`** folder as a vault (Obsidian → *Open folder as vault*); that keeps [[BUGS]] and [[TESTS]] linked too. Start at [[Research Home]].
> `pain-log.csv` is the data. Obsidian can't show a CSV, so read it through [[Pain log]] and the notes in `themes/`. They're regenerated by `node scripts/research/export-obsidian.mjs`; don't edit them by hand.

Open `pain-log.csv` in Excel or Google Sheets when you want to edit, sort or filter it.

**Scripts** (in `scripts/research/`):
- `node scripts/research/collect-github.mjs`: day 1. Pulls the most-upvoted GitHub issues for 19 tools into the log (`collected_by = auto`, `verified = no`).
- `label-prompt.md`: paste it into Codex or Claude to fill summary, role, theme and severity for the auto rows.
- `node scripts/research/export-obsidian.mjs`: rebuilds [[Pain log]] and the theme notes from the CSV. Run after every change.
- `node scripts/research/export-solutions-index.mjs`: rebuilds [[Solutions]] from the solution notes, and fails if any problem isn't covered by exactly one note.
- `node scripts/research/check-log.mjs`: run anytime. Proves the auto rows' quotes, links and 👍 still match GitHub, catches bad IDs, and shows progress toward the targets.

## The method: one pass, 5 days

| Day | Phase | What you do | Output | Time |
|---|---|---|---|---|
| 1 | **Frame + collect automatically** | Confirm questions and evidence window. Run the GitHub collector (top issues of all tools). Skim the reports. | ~550 auto rows (unverified) + 10–20 `report` rows | 2–3 h |
| 2–3 | **Listen** | The 12 listening sessions in manual-playbook.md (Reddit, forums, designers, analysts…) | 15+ rows per role family | ~9 h total |
| 3–4 | **Check the auto rows** + **optional calls** | Spot-check 1 in 5 auto rows. Optionally 3–6 short calls to confirm the top problems. | Verified rows; interview notes | 3–4 h |
| 5 | **Make sense → ideate → decide → report** | Themes, scores, role summaries, brainstorm, decision, final report | synthesis.md, ideas.md, **report.md** | 4–5 h |

After day 5: build the chosen features (each gets a BUGS.md entry and a TESTS.md test). The research is not repeated unless you decide to redo it later.

**When to stop listening:** when the last few sessions for a role add almost nothing new ("saturation"), or the time box runs out, whichever comes first.

## Rules that keep the research honest

1. **Link everything.** No link, no row. A pain you only "feel" is a hypothesis; log it in ideas.md, not the pain log.
2. **Copy their words.** Put the exact quote in `quote`; your interpretation goes in `notes`.
3. **Count people, not posts.** One angry person posting 5 times is 1 person. Use 👍 / upvotes / "+1" replies as `agree_count`.
4. **Stay inside the evidence window** (2025-10-01 → 2026-10-08), and note the tool version. These tools change monthly; if a complaint was clearly fixed before the cutoff, note that in `notes` and give it lower weight.
5. **Look for workarounds.** If people built a script or extension to fix something, it's a strong sign of real pain (and a hint at the solution).
6. **Don't ask leading questions** in interviews: ask about the last time it happened, not "would you like feature X?"
7. **Fix the pain, not just the tool.** "Cursor's context is bad" becomes "the agent forgets decisions between sessions".

## Pain log columns

| Column | Fill with | Example |
|---|---|---|
| `id` | P-001, P-002… | P-014 |
| `date_found` | Today | 2026-10-08 |
| `role` | Role ID from roles-and-tools.md (`?` if unknown) | `fs` |
| `tool` | Tool ID | `claude-code` |
| `source_type` | `github` · `forum` · `reddit` · `hn` · `review` · `x` · `youtube` · `report` · `interview` · `self` | `github` |
| `link` | Direct link to the post or comment | https://github.com/... |
| `quote` | Their exact words (short) | "it keeps asking to trust the folder every time" |
| `pain_summary` | Your one-line neutral summary | Trust prompt repeats for every new worktree |
| `theme` | Theme ID from synthesis.md (fill in later) | `setup` |
| `severity_1to5` | Scale below | 2 |
| `agree_count` | 👍 / upvotes / "+1" replies | 143 |
| `workaround_they_use` | What they do instead | Edit settings.json by hand |
| `netheron_idea` | Optional quick thought | Pre-trust worktrees |
| `notes` | Version, date of post, anything else | Claude Code v2.x, posted 2026-08 |
| `collected_by` | `auto` (collector script) or `manual` (you) | `manual` |
| `verified` | `yes` once **you** have read the source and agree with the row; `no` otherwise. Agents never set `yes`. | `yes` |

## Severity scale (use the same everywhere)

| Score | Meaning |
|---|---|
| 1 | Mild annoyance |
| 2 | Wastes minutes regularly |
| 3 | Wastes hours, or forces a workaround |
| 4 | Blocks work, loses work, or costs real money |
| 5 | Makes people quit the tool, or causes security/data damage |
